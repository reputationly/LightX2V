# RelayVSR_X2 实测:768P → 2K(2026-11-03)

机器:`dev-gpustack-a100-0007`(4×A100-40G,空机,avail 239G)。镜像:`arm64-a100-20261103-0647-e48faec8`
(本次构建的固定版本)。权重:`/nfs-models/wuhanjisuan894/models/RelayVSR_X2`(`wan_x2.safetensors` 10.1G +
`flash_x2.safetensors` 128M)。模型是**上游 LightX2V 自带**(`--model_cls relayvsr_x2`,
`configs/relayvsr/relayvsr_x2.json`),随本次上游同步进了我们的分支。

## 测试素材

`/nfs-data/lx2v_test/relayvsr/`:1280×720(720P)· 24fps · 125 帧(5.2s)/ 374 帧(15.6s)/ 748 帧(31.2s)。
X2 放大后**正好 2560×1440 = 2K**(实测产物 `2560,1440,125/374/748`,帧数与源一致)。

## 结论:4 卡跑不了,上游硬限制

`lightx2v/models/runners/relayvsr/relayvsr_runner.py:41`

```python
if parallel.get("seq_p_size", 1) not in (1, 2):
    raise ValueError("RelayVSR sequence parallelism supports 1 or 2 GPUs")
```

4 卡(`seq_p_size=4`)直接抛错退出。**只支持 1 或 2 卡**,要跑 4 卡得改上游这段代码。

## 1 卡 vs 2 卡(同一份素材,常驻容器内连跑 5 条)

| 片段 | 1 卡(纯推理) | 2 卡(纯推理) | 1 卡(端到端) | 2 卡(端到端) | 2 卡显存/卡 |
|---|---|---|---|---|---|
| 5.2s / 125f | 14.68s | 14.88~15.17s | 56s | 64s | 14169 MiB |
| 15.6s / 374f | 30.92 / 31.03s | **28.67~29.88s** | 72s | 79s | 14169 MiB |
| 31.2s / 748f | 56.64s | **50.37~51.72s** | 97s | 101s | 14169 MiB |

- 1 卡显存峰值 **17051 MiB**;2 卡每卡 **14169 MiB**(−17%)。
- 纯推理:**短片两卡没有收益(≈+2%)**;15s 快 ~5%,30s 快 ~9%。
- 端到端两卡反而更慢:每次请求都要重新起进程、**加载 10GB 权重进显存**(~40-50s),两卡是两份进程,
  这块钱抵消了推理收益。做服务应该常驻(像我们 launcher 那样),不该每请求起进程。
- 连跑 5 条:**显存不涨**(1 卡恒 17051、2 卡恒 14169),无泄漏。

## 首跑成本(带 `use_compile: true` + `warmup: true`)

- 1 卡首条 5s:纯推理 41.66s(含 compile/warmup),后续同长度只需 ~14.7s。
- 2 卡首条 5s:47.52s,后续 ~15s。

# 4 卡可行性验证(2026-11-03 16:45)

## 上游的 seq_p 并行做不到 4 卡,也做不到提速

- 硬限制:`seq_p_size` 只能是 1 或 2(`relayvsr_runner.py:41`),4 卡直接抛错。
- 即使 2 卡,纯推理也只快 5~9%(5s 反而 +2%)。原因是这个模型的耗时主要来自**每个 window 的两帧
  reference 前向**(`self.reference(window[0])` / `self.reference(window[-1])`,走 wan_x2 10GB 模型),
  序列并行切的是单次前向的序列,切不开这部分。

## 块级数据并行(4 卡各跑一段时间段):实测 **2.98×**

把 748 帧(31.2s)的 720P 素材切成 4 段(188/188/188/187 帧),4 张卡各跑一段:

| | 单卡整条(748f) | 4 卡分片(每段 188f) |
|---|---|---|
| 纯推理(稳态) | **56.64s** | **18.7 ~ 19.1s**(四段并行) |
| 冷跑(含 compile) | 41.7s(首条 5s) | 44.7 ~ 46.5s |
| 产物 | 2560×1440 / 748f | 4 段 2560×1440,合计 751f |

→ **56.6 / 19.0 ≈ 2.98×**。差那 1× 的原因是**每段有 ~4.5s 固定开销**(进程启动 + 10GB 权重加载 +
`warmup: true` 的预热):每段 188 帧的纯帧耗时约 56.6×188/748 ≈ 14.2s,实测 19s。
做成**常驻的 4 rank 服务**(一次加载、warmup 只在启动时做)后,固定开销被摊掉,按此推算 ≈ 14~15s,**约 3.8~4×**。

## 两条落地路线

1. **运维层(今天可用,~3×)**:网关侧按时间切片 → 4 张卡并行跑 4 段 → 拼接。不改代码,
   代价是每段都要加载模型、边界处 relay 状态丢失(需要每段多读一个 window 预热再丢弃输出)。
2. **引擎内 chunk_p(推荐,~4×)**:在 RelayVSR runner 里加块级数据并行(一个进程 4 rank,
   rank 各负责连续时间段,段首用 1 个 window 预热、输出丢弃,rank0 拼接),配一个 launcher profile。
   参考我们 SwiftVR 的 `chunk_p_size` 与 SeedVR2 的 `seg_p_size` 实现,需要开发 + 数值/耗时验证。

# 引擎内块级数据并行(chunk_p_size=4)实现与实测(2026-11-03 18:00)

按 SwiftVR 的 `chunk_p_size` / SeedVR2 的 `seg_p_size` 同一套思路,在 `relayvsr_runner.py` 里
加了块级数据并行(提交 `5481c6a9`):`init_parallel` 把 `chunk_p_size` 归到数据并行分支 →
每 rank 只解自己那段连续帧 + 段首多解一个 window 预热(输出丢弃)→ 各写分片 → rank0 拼回。
块并行期间 `check_stop` 改成 rank 本地判定(否则先跑完的 rank 会在 MAX all-reduce 上等满 60s/600s 超时)。

## 实测(720P 1280×720 → 2K 2560×1440,748 帧)

| 方式 | 纯推理 | 端到端 | 显存/卡 |
|---|---|---|---|
| 1 卡 CLI(冷 / 热) | 83.7 / **56.3s** | 187 / 98s | 17.05G |
| 4 卡 chunk_p CLI(冷 / 热) | 49.3 / **23.7~25.3s** | 158 / 74s | 17.18G |
| 1 卡 **常驻服务**(第 2/3 个请求) | — | **50.6 / 51.1s** | 17.05G |
| 4 卡 **常驻服务** | — | **25.3s** | 17.2G |

- **加速比:常驻服务下 50.6 → 25.3s ≈ 2.0×;CLI 纯推理 56.3 → 24s ≈ 2.3×**。
- 成片正确:2560×1440 / 748 帧;拼接(ffmpeg ffconcat + 音轨)只花 1.3s,不是瓶颈。
- 限制线程(`encoder_threads=4` + `OMP_NUM_THREADS=8`)只从 25.3 → 23.7s,说明不是线程爆炸。

## 为什么不是 4×

按 window 拆:1 卡 47 个 window / 50.6s ≈ **1.08 s/window**;4 卡每 rank 13 个 window / 25s ≈ **1.9 s/window**
—— 每个 rank 的 per-window 成本是单卡的 ~1.8 倍。也就是说瓶颈不在「帧数」上,而在**每 rank 的固定/串行开销**:
每 rank 一份 10GB 权重加载、每个 window 两次 reference 前向(走 wan_x2)、再加上 4 个进程争 CPU。

要达到 ~4×,下一步按收益排序:
1. **加大 `clip_len`**(16 → 32/64):window 数按比例减少 → 两边都变快,而 chunk 侧的固定开销被摊薄;
2. **权重共享/单次加载**(`shared_cpu_weights` 或 `load_from_rank0`),把每 rank 的 10GB 加载摊掉;
3. 段边界用更长预热或 cross-fade 融合,把现在 40.3dB 的分块差异补回接近单卡。

## 质量

分块成片 vs 单卡成片:748 帧里 **180 帧逐位相同**,其余 568 帧 **mean 40.34dB / min 38.34dB**。
差异来自段边界 relay 状态(每个 rank 的预热 window 与串行时的历史不同)。要上生产需要先做边界融合或加长预热。

## clip_len 扫描(748 帧,720P→2K,常驻/CLI 均验证;取热态 `RUN pipeline cost`)

| clip_len | 1 卡 | 4 卡 chunk_p | 加速比 | 4 卡每 rank 每 window |
|---|---|---|---|---|
| 16 | 56.41s | 25.29s | **2.23×** | 1.81 s(window 14 个) |
| 32 | 47.08s | **23.40s** | 2.01× | 2.92 s |
| 64 | 56.78s | **22.98s** | **2.47×** | 5.75 s |

- 加大 clip_len **两边都变快**(1 卡 56.4→47.1,4 卡 25.3→23.0),但**加速比卡在 2.0~2.5×**,不是 4×。
- 时钟/功耗排查:4 卡满载 sm 中位 **1380 MHz**、237W/卡;单卡 1320 MHz、249W —— **没有降频/功耗墙**,
  所以「4 卡时每个 rank 变慢 1.5 倍」不是硬件节流。

## 与 SeedVR2 4 卡 ~3.8× 的差别(为什么那个能接近线性)

SeedVR2 的段并行是**互不依赖的帧块**:每段 121 帧、只重叠 8 帧(≈6.6% 冗余),各 rank 跑同一个模型的不同帧块,
没有跨段依赖 → 接近线性。我们实测 124 帧只有 2 段(seg121)所以是 2.4×,而 362 帧切成 4 段时是 4 卡全忙,
量级与 3.8× 一致。

RelayVSR 不一样:它的每个 window 要做**两次 `reference()` 前向**(走 10GB 的 wan_x2)去拿这一头一尾的条件,
window 之间靠 relay 串联。分块后每个 rank 仍要付自己那些 window 的 reference 成本,而且实测每 rank 的
per-window 成本是单卡的 1.5 倍(1.15 → 1.81 s/window,时钟正常),说明还有独占资源的串行开销
(每 rank 解码整条视频才 islice 到自己那段、4 份进程争 CPU 等)。

## 下一步三个方向(按预期收益)

1. **消除每 rank 的整条解码**:现在用 `islice` 跳过前面的帧,等于每个 rank 都解码整条视频;改成 PyAV
   `container.seek()` 直接跳到自己的关键帧,能砍掉大量 CPU 解码与竞争。
2. **定位 4 卡时变慢 1.5× 的那一段**(reference 前向 vs flash decode 分开计时),再决定优化点。
3. **换并行轴:空间切分**(4 卡各出 1/4 画面,带重叠后裁切)—— 与时序 relay 完全无关,预期接近 4×,
   代价是要处理几何/padding 与接缝融合。

## 4 卡 sequence parallel 能不能做?(2026-11-03 21:05 实测)

**技术上能跑,但比单卡慢 6 倍,不能当提速手段。**

- 上游 `seq_p_size ∈ {1,2}` 的根因:flash 解码器的 **KV 只有 2 个头**(`view(-1, 2, 64)`),
  ulysses 按头切时 `2 // 4 = 0`,直接崩;wan 那条 reference 路径本身能切任意卡数。
- 绕过办法:把 flash 解码器切到 **query 并行**(`attention_backend: torch_sdpa`,query 本地、
  K/V 全量 gather,不切头)+ `seq_p_size=4`。放宽守卫后**确实跑通了**,产物正确 2560×1440/748 帧。
- 但实测:**4 卡 seq_p 纯推理 351.6s(vs 单卡 56.4s)= 慢 6.2 倍**;冷跑 372.6s / wall 457~525s。
  原因是 sdpa 替换掉 triton 的 local attention + 每层都 gather 全量 K/V,通信和算子都变慢了。
- 参考:上游 2 卡 seq_p 也只有 1.1×(50.4~51.7s vs 单卡 56.4s)。

**结论**:4 卡提速只有块级数据并行(chunk_p)这一条路走通了——当前 1.78×(对齐版)/2.35×(不预热版);
seq_p 无论 2 卡还是 4 卡都不是有效手段。守卫已恢复成上游的 1/2 卡,避免留一个「能跑但慢 6 倍」的坑。
