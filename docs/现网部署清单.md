## 一.5、节点布局(6节点示例, 按流量调)

```
├─ 节点A: T2V 4卡 ulysses ×1                      (133s/条)
├─ 节点B: I2V 4卡 ulysses ×1                      (68s/条)
├─ 节点C: InfiniteTalk-480p 4卡 ulysses ×1        (54.4s/条)
├─ 节点D: InfiniteTalk-720p 4卡 ulysses ×1        (136.7s/条)
├─ 节点E: VACE ×2(单卡offload, host~55G/实例) + SeedVR2 ×2(单卡, host~42G/实例)
└─ 节点F: Z-Image ×4 / Qwen / 机动扩容
```

- InfiniteTalk 双档 = 不同配置的独立实例, 网关按请求分辨率路由到对应节点
- 节点E host 合计 ~194G, 是唯一贴水位的节点, 上线后盯 MemAvailable
- 扩容优先级按排队情况: I2V(68s最热门)> InfiniteTalk > 其他

**SeedVR2 原子能力注意事项**(改判后新增):
1. **sr_ratio 已开放为请求级字段**(本次出包):默认 2.0, 请求体可传任意倍率, 输出被 config 目标尺寸自动封顶(runner:114 保护)——"480p→1080p"传 sr_ratio=2.25 即可
2. **输入上限**:分辨率 ≤720p(1080p入→4K出显存未验证, 先在 schema/网关侧拦);帧数 ≤121 单段无缝, 超过自动分段(161帧实测质量OK, 且本次已修 PyAV 分段 pts bug)
3. **fps 透传不插帧**:SR 保持输入帧率;原子SR的输入通常是用户已有视频(24/30fps), 不强加 RIFE;16fps 生成片要丝滑请走"生成能力自带的 RIFE"
4. **资源**:显存峰值 ~22.7G、host ~42G, 都便宜——**与 VACE 混部完美**:节点布局 2×VACE + 2×SeedVR2, 同时服务原子SR请求和(画布期的)VACE后处理链
5. video_path 输入链路已在测试中全程验证(harness 走的就是 server 任务体)

**SwiftVR 部署说明**(2026-08-28 实测,拟替代 SeedVR2 成为超分主力;
完整调研与实验数据见 `docs/SwiftVR-实验测试报告.md`):

1. **GPUStack 侧零配置**。`profiles.yaml` 与 `configs/swiftvr/a100/*.json` 都随
   `COPY . /opt/LightX2V` 打进镜像,launcher 按 `(model_cls, gpu_count)` 自动选变体:
   权重目录传 `/nfs-data/models/SwiftVR_lightx2v`(名字含 swiftvr 即可被识别),
   卡数选 1 → `swiftvr/1card`,选 4 → `swiftvr/segp4`。选 2/3 卡会被 launcher 直接拒绝。

2. **一份配置吃所有分辨率**。目标分辨率由请求给,实测同一常驻实例串行处理
   1080p → 2K → 4K → 再回 1080p,切换不用重启、无劣化。

   | 目标 | 单卡 pipeline | 单卡显存 | 4卡 worker | 4卡显存/卡 |
   |---|---|---|---|---|
   | 1080p | 23s | 15.8G (39%) | 9.2-11.0s | ~16.0G |
   | 2K | 37s | 19.8G (48%) | 14.1-17.4s | ~19.8G |
   | 4K | 78s | 32.5G (79%) | 28.7-32.2s | ~33.2G |

2b. **⚠️ 两条路的封顶规则不同(2026-08-28 补,原先缺这层是个必炸的坑)**。

   | 请求形态 | 封顶 | 结果 |
   |---|---|---|
   | 只给 `sr_ratio`(网关默认) | `target_height/target_width` = 1080P 档,按源朝向配长短边 | 横源出 1920×1080、竖源 1080×1920、方源 1080×1080 |
   | 显式 `target_shape` | 仅 `max_target_height/width` = 4K 显存护栏,超了等比压回并 WARNING | 2K/4K 照常放行 |

   为什么 `sr_ratio` 必须封:现网 SR 的分辨率历来不是用户定的,而是引擎按部署档位出片
   —— 网关前端固定下发 `sr_ratio=4.0`(new-api `VIDEO_SR_RATIO_UNCAPPED`,注释原话
   "一个够不着的上限"),指望引擎用 config 档位 min 掉它,SeedVR2 靠
   `seedvr_runner.py:241` 兜住。SwiftVR 早先没有这层,1344×768 的源乘 4 会去出
   **5376×3072(≈5.3K)**,远超 4K/33G 的实测上限,**必 OOM 且不报参数错、跑起来才炸**。
   已实测修复后:同一载荷出 1920×1080/362 帧,显式 `--target_shape 2160 3840` 仍出 4K。

   与 SeedVR2 的一处差异:落档位时 SwiftVR 直接 interpolate 到精确档位尺寸,源与档位
   画幅比不一致时有轻微拉伸(1344×768 的 1.75 → 1.778,即 1.6%);SeedVR2 则是
   `fixed_shape` 上下各裁 12 像素。两种取舍,量级都可忽略,但产物属性都是精确 1080P。

3. **⚠️ 混部按 33G 算,不是按当前请求算**。PyTorch 缓存分配器不把显存还给驱动,
   实例处理过一次 4K 之后占用就停在 32G 不降(实测 4K 后回 1080p 仍占 32.3G)。
   要与别的能力混部,得按最高档预留。

4. **⚠️ 只有一类素材要留给 SeedVR2:细小高速飞溅/粒子**(火花、木屑、水花、碎屑)。
   这类内容上 SwiftVR 会把运动能量压到源以下(木工特写 **-8.7%**,SeedVR2 是 **+12%**),
   观感是颗粒"弹出来"。根因是 ReAE 时间轴 4× 下采样吃掉了亚像素尺度短暂存在的小目标,
   `clip_len` 24→96、`dit_overlap` 0→4、`upscale_mode` 四种实测**均无改善**,配置救不了。

   **不要按"运动剧烈程度"分流** —— 四素材补测(2026-08-28)显示运动最剧烈的雨夜奔跑
   反而是 **+2.3%**(SeedVR2 +14.1%),四条里最贴近源;大面积连贯位移不受影响。
   锐度则是 SwiftVR **四条全胜**(752/400/1848/608 vs 688/271/1376/568)。
   **分流建议**:细小飞溅粒子 → SeedVR2;其余(含大幅动作、体育、人像、静态)→ SwiftVR。
   另:SeedVR2 出片会掉 3~4 帧(362→358/359)且尺寸是 1920×1104,SwiftVR 是 362 帧 / 精确 1920×1080。

5. **吞吐 vs 延迟**:要吞吐就起 **4 个单卡实例**(线性 4×、零通信、零改码);
   四卡一实例只赢单请求延迟(2.1-2.4×)。两者不要混淆。

6. **段并行的实现约束**(评审重点):块按**连续区间**切给各 rank(不是轮转,连续切才能让
   ReAE 因果状态只预热一次),末尾 rank0 按块号 concat 并校验总帧数。
   控制面汇合必须走 **gloo** —— NCCL barrier 不阻塞主机,实测会让 rank0 提前拼接、
   成片只有 97 帧(应 372)。`seg_warmup_chunks` 默认 1,配 `dit_overlap>0` 也安全
   (实测 4卡 vs 单卡平均差 0.303),但**不要调成 0**,否则各 rank 首块会静默丢掉重叠。

7. 输出编码固定 **libx264 / crf12 / preset fast**。上游默认的 x265 打的是 `hev1` 标签,
   Mac 的 QuickTime 与预览**打不开**(文件本身没坏,`-c copy -tag:v hvc1` 可秒级救回);
   而且默认 quality=60 只有 3.6 Mbps,对超分产品等于把刚超上去的细节又压回去。

## 三、部署运维铁律(全能力通用)

1. **多卡禁 cpu_offload**(per-rank pin 爆 host 内存);MoE 禁 load_from_rank0
2. **triton 首请求 per-shape autotune 慢**——实例启动后预热一发再挂流量
3. **错峰启动=必须**(从"建议"升格):压测实锤——4实例同时冷启, 3×T5(11.4G .pth)并发读NFS 18分钟不动;生产实例必须间隔≥2分钟顺序拉起
4. 压测/测数须安静宿主;容器一律 `--memory=240g` 双保险
5. **VACE 三个后续优化杠杆**:①常驻实例(免每请求加载摊销)②SR 流水线化(画布期)③**NUMA 绑定**——双实例各绑一个 NUMA 域(`--cpuset-cpus/--cpuset-mems`+选不同 PCIe 根的两张卡, 先 `nvidia-smi topo -m` 查映射), 隔离 offload 搬运的带宽域, 预期压掉部分 16% 膨胀(InfiniteTalk 2卡+NUMA 实测 +4% 同方向)
6. **TP/PP 判死**:框架有 tensor_p 管线但 wan 系模型未实现(需全线性层切分+int8感知加载=深度工程);无 NVLink 下 TP 每层 2×all-reduce 通信惩罚重(ulysses 只在 attention 边界通信, 正是为 PCIe 选的);PP 无实现+单样本气泡大
6. 观察名单:SekoTalk 权重开放即测(runner/config 现成, 25fps 实时+AR流式);Wan2.2-Animate(需官方预处理管线+decord补丁)
