## 0. 结论（2026-08-30 原文，第 4/5/6 条已按上方状态头作废）

1. **上游报告把"一闪一闪"归给 SwiftVR，是对的；但它把两个症状捆成了一个。实测是两个独立缺陷，分属两个模块：**
   - **时序"两帧一顿"（2beat）= 100% 来自 ReAE 解码器**，DiT 完全无责（拿掉整个 19.9G DiT，2beat 从 0.5631 变 0.5639，纹丝不动）。
   - **暗部"噪点/纹理放大"= 100% 来自 DiT**，ReAE 无责（只跑 ReAE 时 `std_dark` 0.63 ≈ 纯放大对照 0.64，加上 DiT 才变 1.23）。
2. **两个缺陷都在 SwiftVR 模型本体，不是 LightX2V 移植的问题。** 官方 `H-oliday/SwiftVR` 原样跑同素材，指标与我们重合到小数点后三位。上游 LightX2V 也没有相关修复。
3. **可以修**：反相双跑把 2beat 修回 1.00，`restoration_strength` 压住噪点放大，代价 2× 算力、显存不变。
4. **但不该修**：有真值的保真度测试显示，在生产的 768p→1080p 场景下，**纯放大（lanczos）在每一档倍率上都赢 SwiftVR**，1.43× 时赢 14.0 dB。SwiftVR 的输出保真度对输入质量**几乎不响应**（26.0 / 26.4 / 26.8 dB），说明它不是在恢复细节，是在丢掉输入细节重新画一遍。
5. **决策：H3 这类 AIGC 直出素材的超分改用纯放大。** 保留产品上的"超分/画质增强"入口，后端换成 ffmpeg 缩放。成本：**121 帧 1080p 用 4 个 CPU 核 1.91 秒，零 GPU**（对比 SwiftVR 4×A100 4.49 秒）。
6. **这推翻了 `56053435` "拍板 SR 全量走 SwiftVR 不做分流"**。当时的判据是"锐度更高 + 快 11 倍"，而**锐度这个指标量不出沸腾**——幅度涨了但方向是错的。

## 1. 度量口径（先定义，否则下面所有数字不可读）

沿用上游报告 §2 的三个指标，全部先缩放到 **1920×1080** 再量（3×3 高通的物理尺度必须一致）。

| 指标 | 定义 | 读法 |
| --- | --- | --- |
| `2beat` | `d[k]=mean(\|frame[k+1]-frame[k]\|)`，`2beat = mean(d[1::2])/mean(d[0::2])` | 匀速视频恒等于 1.0000；偏离 1 = 两帧一顿。严重程度看 `\|log(2beat)\|` |
| `std_all` / `std_dark` | 高频残差 `hi[t]=frame[t]-boxblur3x3(frame[t])` 的标准差；`dark` = 时间平均亮度最暗四分位 | 高频**幅度**。涨了不代表对 |
| `corr_all` / `corr_dark` | `mean_t(pearson(hi[t], hi[t+1]))` | 高频的**时序相关性**。接近 1 = 真纹理被跟踪；≤0 = 每帧重画（沸腾） |
| `churn` | `(1-corr)/motion` | 按运动量归一化的逐帧重画程度，跨条目比较用 |

度量脚本：`/nfs-output/swiftvr-fix/_diag/measure_compare.py`、`measure_boil.py`。

**门槛**（沿用上游报告 §13.7.3）：G1 `2beat ∈ [0.90, 1.11]`；G5 `std_all ≥ 1.25×` 纯放大对照（保证"还在超分"）。

## 2. 归因：缺陷在哪一层

### 2.1 实验 A —— 把 DiT 整个拿掉

只跑 ReAE 的 encode→decode，不经任何 DiT，走生产完全相同的分块协议（clip_len=24、bilinear 预处理、1920×1080、bf16）。脚本 `_diag/reae_attrib.py`。

| | 2beat | motion | corr_all | std_all | corr_dark | **std_dark** |
| --- | --- | --- | --- | --- | --- | --- |
| synth 双线性对照 | 1.0000 | 0.330 | 0.942 | 6.69 | 0.968 | 6.78 |
| synth SwiftVR 全链路 | **0.5631** | 1.058 | 0.880 | 7.60 | 0.915 | 4.51 |
| **synth 只跑 ReAE，无 DiT** | **0.5639** | 0.902 | 0.930 | 6.21 | 0.954 | 3.53 |
| turbo 双线性对照 | 1.1102 | 4.102 | 0.542 | 3.67 | 0.289 | **0.64** |
| turbo SwiftVR 全链路 | **0.5954** | 5.069 | 0.389 | 7.45 | 0.294 | **1.23** |
| **turbo 只跑 ReAE，无 DiT** | 0.6196 | 3.236 | 0.549 | 3.64 | 0.619 | **0.63** |

**读法**：
- synth 上 0.5631 vs 0.5639 —— 小数点后三位重合。**2beat 与 DiT 无关。**
- turbo 上 `std_dark`：对照 0.64 → 只跑 ReAE 0.63（等于没动）→ 加 DiT 1.23。**噪点放大与 ReAE 无关。**
- 附带：只跑 ReAE 时 `corr_dark` 从 0.289 升到 0.619，ReAE 本身在做正经的时序去噪，是 DiT 把它打回 0.294。

### 2.2 根因：ReAE 解码器的时序上采样按对出帧

`lightx2v/models/networks/swiftvr/reae.py:94` `TemporalGrow.forward`（stride=2）：

```python
y = x.unsqueeze(2)                                  # (T,C,H,W) -> (T,C,1,H,W),帧轴变成 batch 轴
y = F.interpolate(y, size=(2,H,W), mode="nearest")  # 复制成两份
y = self.conv3d(y)                                  # kernel (3,1,1) padding 1,两侧补零
```

3 抽头的时间卷积**被关在每一对内部**，看不到相邻组。代入后：`out[0] = (W1+W2)·x`、`out[1] = (W0+W1)·x`
—— **同一个特征帧的两个固定线性投影**。而解码器最后一个 `TemporalGrow(w2,2)` 之后只剩逐帧的
conv/ReLU/conv（`reae.py:166-170`），**没有任何东西再做时间混合**。所以输出帧天生两两成对：
对内只差一个投影，对间才有真运动 → 帧差 1.4/0.55 交替。

相位也对得上：`frames_to_trim = 3`（奇数），首块解码后裁 3 帧，配对从 (0,1)(2,3) 翻成 (1,2)(3,4)，
所以 2beat < 1 而不是 > 1。这解释了上游报告 §13.6 察觉到的"相位是反的"。

**任何 DiT 注入的瑕疵都只能是周期 4**（DiT 工作在 4× 时间压缩的 latent 率上）。观测到的是纯周期 2，
所以来源必然在最后那次 ×2 时间上采样之后 —— 与实验 A 的结论一致。

### 2.6 顺带定位的两个次要问题

- **`infer_steps` / `target_fps` 被吞（上游报告问题 B）不是 bug，是设计。** SwiftVR 是一步式：
  `INFERENCE_TIMESTEP=1000` 常量、单次前向、没有 sampler，`infer_steps` 在整条路径里不存在，
  三个取值输出 MD5 相同是必然的。`target_fps` 同理：`swiftvr_runner.py:523` 只读 `config["fps"]`，
  请求字段没接，引擎里也没有任何插帧。该修的是 API 层应该拒收而不是静默接受。
- **61 帧崩（问题 C）是我们段并行的真 bug。** 61 帧 → `build_video_chunks` 出 3 块，
  `swiftvr_runner.py:477 _partition_chunks(3, 4)` 给 rank3 分到空区间 `(3,3)`，它开了 writer 又没写帧，
  落一个 0 字节的 `part_003.mp4`，然后 `:709` 的完整性检查报 missing。
  **修法**：块数少于卡数时空 rank 不建分片、`part_paths` 只收非空 rank。**尚未修。**

## 3. 修复方案：探索过程与结论

### 3.1 候选方案全表（turbo，1920×1080）

| 方案 | 2beat | G1 | std_all ÷对照 | G5 | std_dark ÷对照 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| 现状 strength=1.0 | 0.5963 | ✗ | 2.03 | ✓ | 1.93 | 基线 |
| `restoration_strength=0.50` | 0.6096 | ✗ | 1.51 | ✓ | 1.39 | 治噪点不治闪 |
| `restoration_strength=0.25` | 0.6174 | ✗ | 1.25 | 边界 | 1.19 | 同上 |
| 时域 notch3 `[1,2,1]/4` | 0.8867 | ✗ | 1.56 | ✓ | 1.39 | 够不着门槛且糊 |
| 时域窄带 notchIIR r=0.85 | 0.6321 | ✗ | 1.98 | ✓ | 1.86 | **无效** |
| 与原图 50% 混合 | 0.7817 | ✗ | 1.33 | ✓ | 1.17 | 掉锐度且不达标 |
| **反相双跑 strength=1.0** | **1.0019** | ✓ | 1.83 | ✓ | 1.68 | 有效 |
| **反相双跑 + strength=0.50** | **1.0064** | ✓ | 1.40 | ✓ | **1.21** | 全部达标 |

**两条被证伪的猜想**（写在这里防止后来者重走）：
- 「时域 3 抽头陷波能到 0.93」—— 那是在 **ReAE-only** 产物上量的，落到全链路产物只有 0.8867。
- 「窄带 IIR 陷波比 3 抽头更好」—— **反而更差**（0.63）。这个瑕疵不是一根纯 Nyquist 正弦，
  是一整块"配对"结构，窄陷波只挖掉正中那一格。

### 3.2 反相双跑（antiphase）

**原理**：配对格点锁死在 latent 栅格上（1 个 latent → 4 帧 → 2 对）。把输入整体平移 **1 帧**（奇数）
再跑一遍，配对相位翻过来；两遍对齐后取平均，周期 2 分量互相对消，而真实内容在两遍里是同一个，
完整保留。**不是时域滤波**——平均的是同一时刻的两个修复结果，不跨帧混合，不糊运动。

验证方式（离线，未落成代码）：

```bash
# B 路输入 = 首帧复制一份插到最前
ffmpeg -i src.mp4 -filter_complex \
  "[0:v]trim=start_frame=0:end_frame=1,setpts=PTS-STARTPTS[a];[0:v]setpts=PTS-STARTPTS[b];[a][b]concat=n=2:v=1[o]" \
  -map "[o]" -an -c:v libx264 -crf 10 -pix_fmt yuv420p shift1.mp4
# 两路各跑一遍 SwiftVR,然后丢掉 B 路首帧再平均
ffmpeg -i A.mp4 -i B.mp4 -filter_complex \
  "[1:v]trim=start_frame=1,setpts=PTS-STARTPTS[b];[0:v][b]blend=all_mode=average[o]" \
  -map "[o]" -c:v libx264 -crf 12 -preset fast -pix_fmt yuv420p -an out.mp4
```

**成片复核**（量的是最终 mp4，多过一道 x264 编码，数字站得住）：

| | 2beat | std_all ÷对照 | std_dark ÷对照 |
| --- | --- | --- | --- |
| turbo 修改前 | 0.5963 | 2.03 | 1.82 |
| turbo 反相平均 | **0.9982** | 1.82 | 1.60 |
| turbo 反相 + 强度0.5 | **1.0016** | 1.38 | 1.17 |
| synth 修改前 | 0.5654 | 1.11 | 0.67 |
| synth 反相平均 | **0.9774** | 1.11 | 0.65 |

**未达标项**：synth 上 `std_dark` 0.65× 低于 G4 下限 0.7×。那是 ReAE 抹掉 2px 细线造成的"糊"，
不是"闪"，反相平均管不了；真实素材上这项达标。

### 3.3 `restoration_strength`

模型预测的是**残差**（`streaming.py:99` `restored = model_input - strength * pred`），
乘个系数就是在"原样上采样"与"全量恢复"之间做 latent 空间插值。1.0 = 上游原行为。

turbo 上的扫描（`_diag/sweep.log`）：

| strength | 2beat | std_all ÷对照 | std_dark ÷对照 |
| --- | --- | --- | --- |
| 1.00 | 0.5963 | 2.03 | 1.93 |
| 0.75 | 0.6025 | 1.77 | 1.64 |
| 0.50 | 0.6096 | 1.51 | 1.39 |
| 0.25 | 0.6174 | 1.25 | 1.19 |

**2beat 全程几乎不动（0.596 → 0.617）**，再次印证闪烁与 DiT 无关。它只管噪点放大那一半，
而且**只压幅度不改性质**（见 §4.4，corr 始终是负的）。

代码在工作区**未提交**：`streaming.py` 加 `strength` 参数，`swiftvr_runner.py:108` 从
`config.get("restoration_strength", 1.0)` 读。

### 3.4 修复的成本

段并行实测（turbo 124 帧 → 1920×1080，gpu41）：

| 配置 | 单请求耗时 | 吞吐 | restore 阶段 | 每卡 peak_allocated | 每卡 peak_reserved |
| --- | --- | --- | --- | --- | --- |
| 单卡 | 8.75s | 14.17 fps | 7.70s | 13.54 GiB | 14.89 GiB |
| 2 卡段并行 | 5.62s | 22.08 fps | 4.23s | 13.49 GiB | 14.77 GiB |
| **4 卡段并行（现网）** | **4.49s** | **27.64 fps** | 3.08s | **13.54 GiB** | 14.89 GiB |

反相双跑的代价是**耗时不是显存**：两路共用同一份权重（`start_allocated` 恒为 9.402 GiB 就是权重），
两路交替推进所以激活峰值不叠加，真正翻倍的只有 ReAE 的因果状态（各层 MemoryBlock 的上一帧缓存
+ `previous_latents`），1080p 下约 **240 MB**。落法 A（每 rank 自己跑两遍再平均，读帧/编码/concat 不翻倍）
推算 **4.49s → 约 7.6s（1.7×）**，显存 13.54 → 约 13.8 GiB。

> **⚠️ 2026-09-05 实测修正：上面这段显存推算偏低，耗时推算偏高。**
>
> **漏算的是输出缓冲**，不只是 ReAE 因果状态：第一遍的 `restored` 要一直活到第二遍
> `restore_frames` 跑完，`AntiphaseBlender.push` 里的 `torch.cat` 还要再要一块。
> 1080p 每块输出约 300 MB（`24×3×1080×1920×2` bytes）。
>
> | | 推算 | 实测（gpu48，p3 362 帧） |
> | --- | --- | --- |
> | 1080p 单卡 peak_allocated | 13.54 → ~13.8 GiB | 13.54 → **14.04 GiB**（+508 MB） |
> | 4 卡端到端 | 1.7× | **1.27×**（13.55s → 17.20s） |
> | restore 阶段 | — | 1.89×（5.59s → 10.56s） |
>
> 耗时那头比推算**好**：restore 确实翻倍，但读帧/编码/concat/mux 不翻倍，而它们占 4 卡耗时一大半。
> 4K 也测过（25.96 → 27.94 GiB，40 GiB 卡上放得下），但**4K 不是生产档位，不再投入**。

## 4. 推翻：有真值的保真度测试

上面所有指标都是**相对**的——`std_all` 涨了只说明高频更强，不说明**更对**。做一个有 ground truth 的实验。

### 4.1 方法

把 frog 原片（1344×768）降清当"低清输入"，再分别用 lanczos 和 SwiftVR 放回 1344×768，
**拿原片当标准答案**比 PSNR/SSIM。三个倍率覆盖生产实际值与 SwiftVR 的设计工作点。

```bash
# 低清输入(两边都取 8 的倍数,见下方"坑")
ffmpeg -i p3_texture.mp4 -vf scale=944:536:flags=lanczos -c:v libx264 -crf 10 -an lq.mp4
# 对照
ffmpeg -i lq.mp4 -vf scale=1344:768:flags=lanczos -c:v libx264 -crf 10 -an up_lanczos.mp4
# SwiftVR
torchrun --nproc_per_node=4 -m lightx2v.infer --model_cls swiftvr --task sr \
  --video_path lq.mp4 --target_shape 768 1344 --model_path <SwiftVR_lightx2v> \
  --config_json <segp4 配置> --save_result_path up_swiftvr.mp4
# 比对
ffmpeg -i up_X.mp4 -i p3_texture.mp4 -lavfi "[0:v][1:v]psnr;[0:v][1:v]ssim" -f null -
```

> **一个必须避开的坑**：`swiftvr_runner.py:513-514` 会把源裁到 8 的倍数
> （`first_frame.shape[0] // 8 * 8`）再拉伸到 target_shape。第一次用 944×**540** 做低清输入，
> SwiftVR 内部裁成 944×536 再拉到 768，产生 0.75% 的纵向形变，而 lanczos 对照没有这个裁剪 ——
> PSNR 对亚像素错位极敏感，得到的 20.97 dB 是假的，**已作废**。重做用 944×**536**（两边都 /8）。
> 生产的 1344×768 本身 8 对齐，不受影响。

### 4.2 结果

| 放大倍率 | 纯放大 PSNR / SSIM | SwiftVR PSNR / SSIM | 差距 |
| --- | --- | --- | --- |
| **1.43×**（944×536 → 1344×768，= 生产的 768p→1080p 线性倍率） | **40.03 / 0.9842** | 26.01 / 0.8705 | **−14.0 dB** |
| **2×**（672×384 → 1344×768） | **37.22 / 0.9761** | 26.35 / 0.8753 | −10.9 dB |
| **4×**（336×192 → 1344×768，SwiftVR 设计工作点） | **31.15 / 0.9218** | 26.75 / 0.8679 | −4.4 dB |

同一低清输入下的 strength 扫描（2× 档）：

| strength | 1.00 | 0.75 | 0.50 | lanczos |
| --- | --- | --- | --- | --- |
| PSNR | 26.35 | 27.72 | 29.17 | **37.22** |
| SSIM | 0.8753 | 0.8967 | 0.9145 | **0.9761** |

强度越低越接近真值 —— 即"少改一点"就"少错一点"，这本身就说明它改的方向是错的。

### 4.3 最关键的一行：SwiftVR 的保真度是常数

看 SwiftVR 那一列：**26.01 → 26.35 → 26.75**。输入从"几乎没退化"变到"降了 4 倍"，
它的输出离真值的距离**几乎不变**。而 lanczos 老老实实跟着输入质量走（40.03 → 37.22 → 31.15）。

**这说明 SwiftVR 不是在恢复，是在重画** —— 它把输入里的细节丢掉，重新合成到一个固定的
"它认为该有的样子"，输入本来有多好它不在乎。这一条解释了前面所有现象：沸腾、过度生成、
为什么降 strength 有用、以及为什么纯放大看着就够了。

### 4.4 沸腾的直接证据

frog 组（1920×1080，`_diag/boil.log`）：

| | motion | std_all | **corr_all** | churn_all | std_dark | **corr_dark** |
| --- | --- | --- | --- | --- | --- | --- |
| 源（原片） | 12.744 | 2.70 | 0.056 | 0.0741 | 2.09 | 0.069 |
| **纯放大** | 12.710 | **2.71** | 0.037 | 0.0758 | **2.11** | 0.050 |
| SwiftVR 现状 | 15.373 | **5.99** | **−0.037** | 0.0675 | **5.41** | **−0.025** |
| 反相平均 | 14.460 | 4.93 | −0.040 | 0.0719 | 4.41 | −0.024 |
| 强度 0.5 | 13.355 | 4.19 | −0.038 | 0.0777 | 3.59 | −0.022 |

- **纯放大把源的高频原封不动带过来**（2.70 → 2.71，2.09 → 2.11）。
- SwiftVR 把高频幅度翻倍，且时序相关性变成**负数** —— 比随机还差，等于每帧画的纹理跟上一帧无关。
  这就是"沸腾"的量化定义。
- 两个修复方案都只压幅度（5.99 → 4.93 → 4.19），**corr 始终是负的**。它们让沸腾变轻，不让它变真。

## 5. 决策：改用纯放大

### 5.1 纯放大的成本

生产尺度实测（121 帧 = SR 的帧数上限，1344×768 → 1920×1080，lanczos + libx264 crf12，
gpu41，`--cpus` 限核，脚本 `_diag/bench_scale.py`）：

| preset | 线程 | wall(s) | 实时倍数 | maxrss(MB) | 产物(MB) |
| --- | --- | --- | --- | --- | --- |
| ultrafast | 4 | **1.72** | 2.93× | ~440 | 27.9 |
| **veryfast** | **4** | **1.91** | **2.64×** | ~840 | **14.6** |
| veryfast | 16 | 1.89 | 2.67× | ~870 | 14.6 |
| fast | 4 | 3.05 | 1.65× | ~950 | 16.0 |
| medium | 4 | 3.84 | 1.31× | ~1050 | 15.9 |

> `maxrss` 用 `RUSAGE_CHILDREN` 取，是**累计最大值**，所以后面的行继承了前面的峰值；
> 真实的单次峰值就是每个 preset 第一次出现的那个数。量级 0.4–1.1 GB。

成本拆解（8 线程）：**只解码 0.49s，解码+缩放 1.30s** —— 缩放本身约 0.8s，编码约 0.6s（veryfast）。
**线程数超过 4 没有收益**（121 帧 1080p 的 x264 已经跑满帧级并行）。

**对比**：

| | 耗时 | GPU | 每卡显存 |
| --- | --- | --- | --- |
| SwiftVR 4×A100 段并行 | 4.49s | **4 张 A100** | 13.54 GiB |
| SwiftVR 单卡 | 8.75s | 1 张 A100 | 13.54 GiB |
| **纯放大（veryfast，4 核 CPU）** | **1.91s** | **0** | ~0.8 GB 内存 |

**纯放大比 4 卡 SwiftVR 还快 2.4 倍，且不占任何 GPU。**

**A100 上没有硬件编码器**，实测 `h264_nvenc` 报 `Cannot load libnvidia-encode.so.1`
（A100/GA100 只有 NVDEC 没有 NVENC）。所以编码必须走 CPU —— 但如上，CPU 完全够。

### 5.2 现在生产里没有"纯放大"这条路

`RUNNER_REGISTER` 里没有任何 model-free 的 SR runner，SR 请求一律进模型（`swiftvr` / `seedvr2`）。
网关侧（new-api `web/classic/src/hooks/videoPlayground/useVideoGeneration.js:1058`）在
"画质增强"这一段发的是：

```js
{ task_type: 'sr', video: `task:${prevTaskId}`,
  sr_ratio: VIDEO_SR_RATIO_UNCAPPED /* 4.0 */,
  resize_mode: VIDEO_SR_RESIZE_MODE,
  ...(targetShortEdge > 0 ? { target_short_edge } : {}),
  ...(interpolation ? { target_fps } : {}) }
```

**所以"纯放大"需要新增，不是切个开关。**

### 5.3 三种落法

| 落法 | 做什么 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 新增 LightX2V runner** `RUNNER_REGISTER("upscale")` | task 仍是 `sr`，内部只做 `F.interpolate` / ffmpeg 缩放，复用现有 `resolve_output_size`（target_shape / target_short_edge / sr_ratio 三条路） | **网关零改动**，`/v1/tasks/video/` 契约不变，档位封顶逻辑照搬 | 仍占一个 gpustack 实例槽（可部署成 CPU-only） |
| **B. 网关侧直接做** | new-api 在 upscaling 段调 ffmpeg，不发 SR 请求 | 省掉一整跳 | 网关要具备 ffmpeg 与视频落盘能力，SR 的档位/封顶规则要重新实现一遍 |
| **C. 生成端直接出目标分辨率** | 让 H3 直接生成 1080p，取消超分段 | 最干净，没有二次重采样 | 需确认 H3 能不能出 1080p 且成本可接受（属 vllm-omni 侧，未验证） |

**建议 A**：改动面最小，档位规则（`_oriented_target` / `_clamp_to_ceiling` / `target_short_edge`
三条优先级）已经在 `swiftvr_runner.py:186-245` 写好并经过现网验证，直接复用；而且它可以部署在
CPU-only 节点，把 4 张 A100 完全释放出来。**C 值得并行评估**——如果 H3 能直出 1080p，
连一次重采样都省了，是理论最优。

### 5.4 SwiftVR 什么时候还该用

**不要因此把 SwiftVR 删掉。** 它输的是"干净素材 + 小倍率"这个组合：

- **干净输入**：H3 是生成式模型的直出，没有压缩块、没有传感器噪点、没有真实失焦。
  SwiftVR 在**重退化**数据上训练，把苔藓纹理、水珠、颗粒当成"要修的退化"重画。
- **小倍率**：1344×768 → 1920×1080 线性只有 1.43 倍，本来就没多少信息缺失需要重建。
- 4× 档差距收窄到 −4.4 dB，配合生成式超分的感知优势，**在真实退化素材 + 大倍率上很可能是正收益**。

**建议的分流规则**：用户上传的真实视频（可能有压缩/噪点/糊）或 ≥3× 的放大走 SwiftVR；
平台自己生成的 AIGC 素材 + ≤2× 放大走纯放大。这条规则**尚未用数据验证**（我只测了 AIGC 素材），
落地前应当在真实退化素材上补一组同样的真值测试。

## 6. 保留意见与可能的反驳（给验收者）

请重点挑战下面这些点，它们是本报告最脆弱的地方：

1. **PSNR/SSIM 天然对生成式超分不利。** 这是公认的 perception-distortion tradeoff：
   生成式模型画出"合理但不逐像素相同"的纹理会被扣分，人眼却可能觉得更好。
   **我的答辩**：这里 PSNR 低是跟**负的时序相关性**（§4.4）一起出现的 —— 编出来的细节连帧间稳定
   都做不到，那就不是"合理纹理"而是沸腾。对视频这两条加起来才是决定性的，单看 PSNR 我不会下这个结论。
   **反驳这条的正确方式**：拿一个感知指标（LPIPS / DISTS）重测，或组织盲测。我没做感知指标。
2. **只测了一条素材做真值实验**（frog）。turbo、synth 没做真值测试。frog 是高频纹理最密的一条，
   可能是最不利于 SwiftVR 的样本。**应当在 p1_craftsman / p2_motion / p4_lowlight 上补测。**
3. **降清方式是 lanczos，属于"干净退化"。** 真实退化（压缩、噪点、运动模糊）下 SwiftVR 可能翻盘。
   §5.4 的分流规则就是因此提出的，但它本身没有数据支撑。
4. **`churn = (1-corr)/motion` 是自定义指标**，不是通用度量，跨素材比较时要小心。
   frog 的源 `corr_all` 只有 0.056，因为风吹叶动本身运动极大，corr 已接近去相关；
   这条素材上 corr 的绝对值意义有限，**`std_all` 翻倍才是主要证据**。
5. **1.43× 那个点返工过一次**（§4.1 的坑）。第一次 20.97 dB 作废，第二次 26.01 dB。
   验收时请用 `up143b_*`（8 对齐）那组，不要用 `up143_*`。
6. ~~**反相双跑没有落成代码**，所有"修改后"成片都是跑两遍 + ffmpeg 平均合出来的。
   真落到 runner 里，chunk 边界与因果状态的交互需要重新验证。~~
   **2026-09-05 已落成**（`AntiphaseBlender` + runner 起第二条 restorer）。当初担心的
   "chunk 边界与因果状态的交互"确实是主要难点，处理方式：两条流各持一份因果状态但共享权重
   （状态由 `run_causal_layers` 外置穿传，模块本身无状态）；移位流第 j 帧对应正相第 j-1 帧，
   配对差一格，用 carry 跨块传本块末帧；段并行下各 rank 的 carry 由预热块产生，
   因此 `antiphase_dual_pass` + `seg_p_size>1` 强制 `seg_warmup_chunks>=1`。
   验收：输出与本文的离线三步流程 43.83 dB；关掉开关时与改前产物 **md5 逐位相同**。
7. **性能数字是单节点单请求**，没有并发压测。CPU 纯放大在多路并发下的表现（尤其 x264 的核竞争）
   未测。
