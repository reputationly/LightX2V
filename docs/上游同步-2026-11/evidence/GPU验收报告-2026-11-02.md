## 2. 三条未达标 / 阻塞项

### 2.1【高】SeedVR2 4 卡「前处理阶段」被取消 → 服务级死锁
现象:POST + DELETE 都返回 200/正常,任务状态 = `cancelled`,但 rank0 推理线程提前退出,其余 3 个 rank
卡在段边界交换;`utilization.gpu=0%`,processing lock 永不释放,紧随其后的请求 6 分钟仍 `pending`,只能重启容器。

现场(`evidence` 外,机上 `/data/verify-logs/A2_cancel_hang_evidence.txt`):
```
rank0: ep_poll ; rank1-3: futex_wait_queue_me ; GPU util 0%
rank0 独缺 "decoded video shape=..." 日志
```
复现:
```bash
bash verify/serve.sh new seedvr2-3b/seg121-4card 4 18000
bash verify/sr.sh 18000 assets/sr_768p_15s.mp4 out.mp4 '"sr_ratio":4.0' 20   # 20s 后 DELETE
# 再发任意小请求 -> 永远 pending
```
denoise 阶段取消(A2c)与 SwiftVR 取消(A3b)都正常,说明是**前处理路径上的 rank 不同步**:
有 rank 在前处理里提前返回/抛错,其余 rank 继续走到段边界 P2P 形成永久等待。
**未修**(需要改分布式退出语义,超出"只验证"范围)。

### 2.2 SwiftVR 4C↔1C 49.28dB(<50dB 判据)
失分集中在 chunk 边界帧(24/48/72/96)。差 0.7~2.3dB,肉眼不可判,但没到文档的门槛。

### 2.3 SeedVR 4C↔1C 46.30dB:两份 profile 的 `vae_tile_size` 不同,该判据当前不可测
```
diff configs/seedvr/a100/seedvr2_3b_seg121.json configs/seedvr/a100/seedvr2_3b_segp4.json
-    "vae_tile_size": 384
+    "vae_tile_size": 512 ; + "vae_memory_limit_gb": 0 ; + "parallel": {seg_p_size:4}
```
分块 VAE 编解码本身就有逐帧 45.6~48dB 的差异,且**全片均匀**(没有"第 58 帧之后劣化"的特征),
可排除 segment 噪声 keying。要验证文档那条 inf,需让 4 卡 profile 也用 384(改配置,未做)。

## 3. 环境类发现(不是代码问题,但影响判据与生产)

1. **线程数默认值会假慢 2.3×**:未限定时 torch 每 rank 起 128 线程 × 4 rank,124f/768p 从 69s 劣化到 **228.2s**;
   加 `-e MALLOC_ARENA_MAX=2 -e OMP_NUM_THREADS=8` 回到 69.0s(与 old 持平)。**建议写进 launcher/镜像 ENV**。
2. **宿主内存**:§8.4 的"145G/节点"是整机口径;本集群邻居已占 92G,0004 上发生过一次内核 OOM
   (4 rank 各 ~18G RSS + 12.5G shmem)。验收改用「同机 old vs new 比值」口径。
3. **显存贴边**:SeedVR2 300f(3 段)峰值 40341/40960 MiB(98.5%);SwiftVR sh=2160 峰值 39269 MiB(96%)。
4. `serve.sh` 自身两个 bug(已修在仓库副本):profile 含 `/` 导致日志重定向失败;就绪等待 450s 短于冷启动 ~570s。
